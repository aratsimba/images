I think the current two-button approach is actually better UX than the proposed change. Here's my reasoning:
Why the current design works well:

    Fewer clicks — Users go directly to the form they need in one click (current) vs. two interactions (proposed: click button → select radio → form appears)
    Clear intent — The two buttons make it immediately obvious what types of entries exist in the system
    No ambiguity — There's no decision fatigue; users already know whether they're adding a person or company before they click

Why the radio button approach would be worse:

    Adds friction — An extra intermediary step for something users do frequently
    Radio buttons feel "form-like" — Starting a creation flow with a meta-choice before the actual form feels indirect
    No real simplification — Two buttons in a toolbar isn't cluttered; it's informative

A better alternative if you want to simplify:

If the goal is to reduce buttons in the action bar, a single "＋ Add" button with a small dropdown menu would be a good middle ground:

    Click "＋ Add" → a compact 2-item dropdown appears: "👤 Person" / "🏢 Company"
    Selecting an option goes directly to the form (same as today, but consolidated into one button)
    This saves horizontal space while preserving the one-click-to-form efficiency

This pattern is common in apps like Google Contacts, Notion, and CRMs — a single "New" button that fans out into entity type options.

Removing a member triggers cascading side effects — address stripping, primary reassignment, and potentially full household dissolution. Capture a snapshot of the affected records before the operation and restore them if the user clicks Undo before the timer expires. This is especially important for the ≤2 member case where the entire household is deleted and the other member's address is permanently relabeled.


===================

Add a separate "Households" view to manage households. This view shows the list of available households and allows the following actions:

1) Create a new household. A household has a name and an address which are both required.

2) Add a household member. A household must have at least two members. One of the household members must be a primary contact. A household has one and only one primary contact.

3) Remove a household member according the following rules:

A) If the member is the primary contact, another member must be selected to be the primary contact.

B) If this is the last member, change the address type of the primary address of all members from "Household" to "Home" before removing the member. This ensures that the "disconnected" member still has a primary address.

C) In all cases, present a confirmation dialog that describes what the delete action will do.

4) Change household address. If the address is changed, make sure to synchronize the primary address of all of the members.

5) Delete a household. This removes all household members according to action 3) and then deletes the household. Present a confirmation dialog that describes what the delete action will do.

Additional requirements:

- When a household is saved (not deleted), keep its address in sync with the members' primary address. If necessary, update (or add) the primary address of all of its members with the household address and an address type of "Household". All household addresses have a type of "Household" in each member's primary address.

- On the Person Edit form, remove the "Household Members" section and add a new section named "Household Membership". This new section displays the person's current household name and members. If the person is not part of a household, it allows the user to assign a household to the person. It uses a search box that lists the available households by name. When a name is selected, this has the same effect as adding the person to the household. The user can leave the household membership blank if the person does not belong to a household, and this has the same effect as removing the person from a household.

- In all person and household management actions, make sure that there are no unresolved or dangling references between Persons and Households.

Auto-archive with configurable retention period

Add an auto-archive feature for deceased entries with a configurable retention period. Include a settings panel where users choose the retention period (e.g., 90 days, 6 months, or 1 year after date of death), a visual countdown or 'days remaining' indicator on deceased entries, a separate 'Archived' view to browse past entries for historical reference, and an option to manually restore an archived entry back to active/deceased status.


--------

Directory Analytics Dashboard

Add a summary analytics dashboard at the top of or alongside the list view with quick insights about the directory. Include total contacts breakdown (persons vs. companies, active vs. deceased), age distribution chart (members in each decade), geographic heatmap or breakdown by state/city, household size distribution, upcoming anniversary milestones (e.g., 25th, 50th wedding anniversaries), and growth over time (new entries per month). This gives directory administrators a bird's-eye view without needing to export data to a spreadsheet.


-----

Tags & Custom Groups

Add a flexible tagging and grouping system beyond the existing type and household structures. Include free-form tags on any entry (e.g., 'choir', 'youth group', 'volunteer', 'board member', 'small group A'), the ability to filter the directory by one or more tags, bulk-email list generation that selects a tag and exports all email addresses in that group for newsletter tools, and tag-based views/tabs for quick access to commonly used groups. This is especially useful for church or organization directories where people belong to multiple overlapping groups that don't map neatly to households or companies.

Add a light/dark theme toggle in the header that persists across sessions using private storage. Dark mode would reduce eye strain for users managing their directory in low-light environments and demonstrate the app's use of user-specific preferences.

When sorted by name, group entries under sticky letter headers (A, B, C…) with a compact clickable letter index along the side for instant scrolling to a specific section. This would complement pagination by making it easier to locate contacts within a page.
